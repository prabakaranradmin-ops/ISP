# Native Windows install

Scripts and binaries for running this system on a single Windows machine with
no Docker. `ISP-BSS-Setup.msi` (built from [../installer/](../installer/README.md))
drives these in order; they are documented and runnable by hand so an install
can be reproduced or debugged without one, or without building the MSI at all.

## What a native install consists of

| Piece | Where it comes from | Notes |
|---|---|---|
| `api_service.exe` | `go build ./cmd/api` | HTTPS API, subscriber portal, staff console, captive portal |
| `aaa_core_daemon.exe` | `go build ./cmd/radiusd` | RADIUS AAA, the task worker pool, and every background scanner |
| `bootstrap.exe` | `go build ./cmd/bootstrap` | Run-once: applies migrations, generates secrets |
| `pgsql\` | PostgreSQL 15 Windows **binaries** zip | Server only; no separate PostgreSQL install |
| Chromium | bundled (Phase 5) | Invoice PDF rendering |

Nothing else is required at runtime. Redis and Caddy were removed in earlier
phases: the caches are in-process (`internal/localcache`), live session state
and the task queue are tables (migrations 036 and 037), and the API terminates
TLS itself (`pkg/tlscert`).

## Install order

The order matters — each step needs the previous one to have finished.

```powershell
# 1. Provision the database: initdb, loopback-only config, service, createdb.
.\setup_postgres.ps1 -InstallDir 'C:\Program Files\ISP BSS' -SuperuserPassword '<generated>'

# 2. Migrate and generate the application's secrets.
.\bootstrap.exe `
    -superuser-dsn 'postgres://postgres:<generated>@127.0.0.1:5432/isp_bss_oss?sslmode=disable' `
    -config-dir 'C:\ProgramData\ISP BSS\config'

# 3. Register both services and start them.
.\register_services.ps1 -InstallDir 'C:\Program Files\ISP BSS' -ConfigDir 'C:\ProgramData\ISP BSS\config'
```

The superuser password is generated by the installer and used only by steps 1
and 2. The services never receive it: `bootstrap` provisions the
least-privilege `bss_app` role (migration 019) and writes a DSN for *that*
role into `app.env`. That separation is the point — row-level security on
`lea_audit_log` exempts superusers, so an application connecting as one would
silently bypass the append-only audit guarantee.

## What bootstrap generates

Into `-config-dir`:

- `app.env` — `DB_DSN` (as `bss_app`), `AES_KEY_STORE_URL`, and the four
  signing secrets (`JWT_SECRET`, `PORTAL_JWT_SECRET`, `RADIUS_SECRET`,
  `RADIUS_VERIFIER_SECRET`).
- `keys\aes_keys.json` — the AES-256 key store protecting NAS secrets, KYC
  data and webhook signing secrets at rest.

Integration credentials (WhatsApp, SMS, Razorpay, SMTP) are **not** generated;
they belong to accounts an installer cannot create. Add them to `app.env`.
Each unset one disables its own feature and says so at startup rather than
failing it.

## Running as Windows services

Neither `api_service.exe` nor `aaa_core_daemon.exe` gets its configuration
through the environment the way it would under Docker Compose or a
developer's shell — the Service Control Manager execs a binary directly with
a fixed environment and no shell runs in between, so there is no moment where
anything would source `app.env` for it. Both binaries instead take an
`-env-file` flag (`internal/envfile`) and read the file themselves; a real
environment variable, if one happens to be set, still wins over whatever the
file says, exactly like sourcing a shell script would behave.

`register_services.ps1` is what points that flag at the install and does the
rest of what a Windows service needs beyond the binary itself: an Event Log
source for `internal/winservice`'s startup-failure logging (there is no
console under the SCM to print to), a per-service `LOG_FILE` set through the
service's own registry `Environment` value so both services' ordinary logs
land in separate files, a dependency on the PostgreSQL service so Windows
starts it first, and a restart-on-crash recovery action.

Detecting which mode to run in is automatic. `winservice.IsWindowsService()`
(`internal/winservice`) is true only when the SCM itself started the process
under one of the names `register_services.ps1` registers; running either
binary from a console — by hand, or under `-SkipService`-style manual
testing — takes the same interactive path (Ctrl+C / SIGTERM) it always did.

### Why every path a service touches has to be absolute

A Windows service's working directory is always `%SystemRoot%\System32`,
never the install directory — the SCM does not offer a per-service "start
in" folder the way Scheduled Tasks do. Anything read from a relative path
resolves against System32 instead of wherever an operator actually expects
it, which is invisible in ordinary interactive testing (running a binary
from its own directory makes the two indistinguishable) and only shows up
once something registers it as a real service.

Two things this system generates were caught doing exactly that:

- `cmd/bootstrap`'s `-config-dir`/`-keys-dir` are resolved to absolute paths
  before anything is written, specifically because `AES_KEY_STORE_URL`
  embeds one of them verbatim into `app.env`. A relative `-config-dir` used
  to produce a relative `AES_KEY_STORE_URL` that only happened to work when
  `bootstrap.exe` and the service were run from the same directory —
  confirmed broken by running `api_service.exe` from an unrelated directory
  with the app.env this used to produce: it failed to start, unable to find
  its own key store.
- `TLS_CERT_DIR` (`internal/config`) defaults to the relative `./config/tls`
  — fine for a developer running the binary from its own directory, not for
  a service. `register_services.ps1` sets it explicitly, absolute, through
  the API service's registry `Environment` value (`aaa_core_daemon` never
  reads it, so it gets none). Confirmed broken the same way: without it, the
  self-signed certificate got written under a `config\tls` next to whatever
  directory the process happened to be started from.

## Upgrades

Re-running all three steps is safe and is what the MSI does:

- `setup_postgres.ps1` leaves an existing cluster and database alone, and
  starts the server only if it is not already running.
- `bootstrap.exe` applies only migrations that are new (goose's own version
  table) and **never** rotates a secret once `app.env` exists.
- `register_services.ps1` stops each service before reconfiguring it (its
  binary path may have moved) and leaves the Event Log source and recovery
  action alone if already present.

The second guarantee is load-bearing. Regenerating the AES key store would
make every already-encrypted column unreadable, and regenerating the `bss_app`
password would lock out services mid-upgrade. If exactly one of `app.env` and
`aes_keys.json` is present, `bootstrap` refuses to run rather than recreating
the missing half — restore it from backup instead.

## Verifying an install by hand

```powershell
# The API answers over HTTPS, TLS 1.3 only.
curl.exe -sk https://127.0.0.1/readyz          # {"status":"ready"}

# RADIUS is listening on auth and accounting.
netstat -an | Select-String '1812|1813'

# The app role is genuinely least-privilege: this must be denied.
psql -d '<DB_DSN from app.env>' -c 'DELETE FROM lea_audit_log;'
```

## Running the scripts without touching machine state

`setup_postgres.ps1 -SkipService` starts the server directly instead of
registering a Windows service, which is how the install is exercised on a
development machine. Pair it with `-Port` and an `-InstallDir` outside
`Program Files`:

```powershell
.\setup_postgres.ps1 -InstallDir D:\isp-test -SuperuserPassword pw `
    -Port 15433 -SkipService
```

`register_services.ps1 -DryRun` prints what it would do — including the
exact `binPath` each service would be registered with — without creating an
Event Log source, a service, or starting anything. It still needs a real
`app.env` at `-ConfigDir` and the two `.exe` files at `-InstallDir` to reach
that point; both are checked before anything else, dry run or not.

Registering, starting, and stopping a real Windows service needs an elevated
prompt — there is no dry-run substitute for that half. `-DryRun`'s value is
catching a wrong path or a missing prerequisite before an elevated run, not
replacing one.

## Onboarding a router (NAS)

`new_nas_registration.ps1` generates a strong RADIUS secret and prints two
copy-paste blocks: the fields for the console's Routers screen, and the
matching RouterOS commands for the router's own side — so both ends get the
identical secret without typing a 16+ character string twice by hand.

```powershell
.\new_nas_registration.ps1 -RouterIP 192.168.88.1 -Description 'Main office'
```

Prompts for anything not passed as a parameter. Needs no elevation — it only
generates and prints text, it does not touch the running BSS or the router.
See `specification_docs_v2/23_MTK_MikroTik_Integration_Guide.md` for the full
background.

## A note on the scripts' encoding

Both scripts are deliberately ASCII-only. Windows PowerShell 5.1 reads a
`.ps1` as ANSI unless it carries a UTF-8 BOM, so a non-ASCII character in a
comment becomes a parse error rather than a typo — and a BOM does not reliably
survive every editor and copy that touches a file.
